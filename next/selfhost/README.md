# QWIZ-PARTY — изолированный self-hosted Supabase: инструкция испытания 40 участников

**Статус:** подготовлена безопасная тестовая конфигурация. В этом PR **не развернут сервер**, не скопированы реальные пользователи, не выполнена миграция базы и не переключен production. Основная игра, ГОС.ID, домен и ключи действующего облачного Supabase не меняются.

## Зачем отдельный стенд

По протоколу `next/docs/load-test-40-20261026.md` облако уже прошло 40/40 отправок ответов (p95 = 2073 мс), 40/40 чтений комнаты (p95 = 2660 мс), 40/40 подтверждений и 40/40 отказов в повторной записи. Это были виртуальные клиенты одного GitHub runner, а не 40 физических смартфонов и не 40 долгоживущих WebSocket-подключений. Self-hosted не объявляется быстрее до сопоставимого измерения.

## 0. Условия

- **Отдельный** Linux-хост, рекомендовано 4 CPU / 8 ГБ RAM / 80 ГБ SSD.
- Собственные домен/адрес, HTTPS (кроме localhost при локальной проверке), Docker Engine и Compose.
- Отдельная тестовая БД, отдельные JWT/API-ключи и **только фиктивные** игроки и вопросы.
- Стабильная сеть и корректно настроенный Auth anonymous sign-in rate limit для 40 новых сессий с одного IP.
- Порты Postgres, Realtime internals, Studio не публиковать в Интернет без контроля доступа; API — за reverse proxy с TLS.
- **Не выполнять** SQL из `next/migrations/` по алфавиту. Там есть исторические, повторно определяющие RPC, QA rollback и MANUAL-скрипты, а функции QWIZ зависят от уже существующих объектов в общей БД.

## 1. Установка тестового Supabase (на отдельном сервере)

Используйте актуальный **официальный** Docker-стек; не копируйте старый compose из сторонних статей. В 2026 году по умолчанию используется Envoy вместо Kong. Перед выполнением просмотрите официальный скрипт:

```bash
curl -fsSL https://supabase.link/setup.sh -o /tmp/supabase-setup.sh
less /tmp/supabase-setup.sh
sh /tmp/supabase-setup.sh
cd supabase-project
sh run.sh start
docker compose ps
```

Официальная инструкция: https://supabase.com/docs/guides/self-hosting/docker

Установщик сам генерирует ключи и настройки, в том числе `SUPABASE_PUBLISHABLE_KEY`; при ручной установке нужно отдельно запустить скрипты генерации секретов согласно официальным инструкциям. Настройте `SUPABASE_PUBLIC_URL`, `API_EXTERNAL_URL` (включая `/auth/v1`) и `SITE_URL`, домен и HTTPS. Ключи не печатать в чат, не коммитить в GitHub. Учесть отдельные правила обновления версии PostgreSQL и конфигурации Supabase.

Проверить контейнеры и диагностику: `docker compose ps`, `sh run.sh logs`.
Для полной локальной лаборатории не требуется публично доступный VPS, но сервер и браузеры должны видеть API по подходящему HTTPS-адресу.

## 2. Схема QWIZ без реальных пользователей

**Сначала копия схемы, затем синтетические данные**. Исходный cloud Supabase обслуживает не только QWIZ-PARTY, но и ГОС.ID. Для тестового стенда допустимо экспортировать схему общего проекта, но не переносить реальные аккаунты, результаты и персональные данные.

Для актуальной версии Supabase CLI (проверить `supabase --help`, `supabase db --help`):

```bash
# CLOUD_DB_URL и STAGING_DB_URL задать локально, не сохранять в репозитории.
supabase db dump --db-url "$CLOUD_DB_URL" -f roles.sql --role-only
supabase db dump --db-url "$CLOUD_DB_URL" -f schema.sql
# НЕ выполнять экспорт данных или auth.users для первого теста.
psql --single-transaction --set ON_ERROR_STOP=1 --file roles.sql --file schema.sql --dbname "$STAGING_DB_URL"
```

Импорт выполняется **только в пустой изолированный экземпляр**. При несовпадении версий PG, extensions, ролей или объектов Auth нужно остановиться и адаптировать перенос, а не игнорировать ошибки. Схема включает определения функций, RLS, таблиц; данные, учётные записи и Storage объекты здесь намеренно отсутствуют. Переменные среды, дампы, SQL-подключения и аутентификационные секреты хранить вне GitHub.

Руководство: https://supabase.com/docs/guides/self-hosting/restore-from-platform

Создайте тестового преподавателя с **правильными правами по текущей модели проекта**, тестовый набор и комнату с **точным названием**:

```text
QWIZ LOAD 40 · disposable fixture
```

Тестовый код комнаты — 8 символов из `A-F0-9`. Прежде чем запускать полный тест, убедитесь, что конкретно в этой комнате `org_next_join`, `qwiz_party_state`, `org_next_answer`, `qwiz_party_projection` доступны и работают. Не отключайте RLS и не назначайте service-role ключ браузерам или тестовым игрокам.

## 3. Проверка защиты от ошибочного подключения

Из корня **тестовой копии репозитория**:

```bash
node --test next/selfhost/target.test.mjs
node --check next/live-40-supabase.mjs
node --check next/selfhost/prepare-preview.mjs
```

Новый режим `QWIZ_LOAD_TARGET=selfhost` требует `QWIZ_LOAD_CONFIRM=ISOLATED_SELFHOST_ONLY` и отдельные `QWIZ_LOAD_URL` и `QWIZ_LOAD_KEY`. Он отказывается подключаться к `*.supabase.co`, запрещает service-role/secret key, запрещает HTTP вне localhost. Старый облачный ручной CI-сценарий сохранен без изменения настроек.

Установка SDK для теста: используйте отдельный test checkout; установите и **зафиксируйте конкретную версию** `@supabase/supabase-js` в `package-lock.json` (не использовать `@latest` для воспроизводимого запуска).

## 4. Локальная копия фронтенда — без изменения production

Задайте переменные окружения **только в терминале тестового стенда**, используя реальные значения из изолированного Supabase:

```bash
export QWIZ_LOAD_TARGET=selfhost
export QWIZ_LOAD_CONFIRM=ISOLATED_SELFHOST_ONLY
export QWIZ_LOAD_URL=https://qwiz-test.example.org   # ЗАМЕНИТЬ на собственный стенд
read -sr QWIZ_LOAD_KEY; export QWIZ_LOAD_KEY            # Вставить publishable key и нажать Enter
```

Создайте отдельную копию статического интерфейса с подстановкой адреса и публичного ключа:

```bash
node next/selfhost/prepare-preview.mjs
python3 -m http.server 8088 --directory visual-artifacts/qwiz-selfhost-preview
```

Открывать: `http://localhost:8088/ORG/next/`. Исходные `next/*.js` не изменяются; тестовая сборка сохраняется внутри игнорируемого `visual-artifacts/`. Если проверяете на реальных смартфонах, используйте отдельный **HTTPS-адрес предпросмотра**, не production GitHub Pages: иначе доступ по локальному `localhost` с телефонов невозможен, и возможны ограничения mixed content. Возможные внешние CDN-зависимости интерфейса сохраняются: этот режим **не гарантирует полностью офлайн-работу**.

## 5. Измерение 40 игроков на изолированной комнате

С существующей ограниченной программой `next/live-40-supabase.mjs`:

```bash
export QWIZ_LOAD_ROOM=A1B2C3D4     # ЗАМЕНИТЬ на код фиктивной комнаты
QWIZ_LOAD_MODE=public node next/live-40-supabase.mjs
QWIZ_LOAD_MODE=full node next/live-40-supabase.mjs
```

Режим `public`: 3 × 40 одновременных чтений состояния. Режим `full`: 40 независимых анонимных входов и присоединений, 40 чтений, прерванные HTTP-запросы и повторные чтения, 40 одновременных ответов и 40 попыток повторного ответа. **Перед ответами скрипт ждёт, когда преподаватель вручную запустит вопрос в тестовой комнате.**

Проверка точного названия комнаты до запуска любого режима обязательна. Не использовать учебную комнату. Каждый запуск `full` создаёт новых анонимных пользователей. После теста отдельно удалить **только** созданные тестовые аккаунты и комнату; проверить отсутствие тестовых записей. При ошибке лимита регистрации сперва исправить настройки **тестового** Auth, а не запускать тест бесконечно.

Важное ограничение: скрипт **не измеряет** 40 постоянных WebSocket-подключений и полный игровой сеанс на физических смартфонах. Эти проверки выполняются следующим этапом после подготовки доступа к серверу и тестовым устройствам.

## 6. Критерии приёмки

Отдельно записывать p50, p95, p99, максимум и число ошибок каждого этапа. Для сопоставления с облаком использовать *те же* сценарии, количество клиентов, расположение генератора запросов и прогретый сервер. Приёмочные условия:

1. 40/40 игроков авторизуются и входят; 40/40 ответов принимаются; 40/40 подтверждений; повторные записи не повышают очки; утечки правильных ответов отсутствуют.
2. Проводится отдельный эксперимент с 40 одновременными WebSocket-подключениями, обрывом соединения и возвратом к правильной фазе, без дублирования результатов.
3. Сравниваются задержки облачного и локального сервера. **Меньший p95 не гарантирован**, пока измерение не завершено.
4. Полный цикл от лобби до финала проходит с 40 устройствами без зависаний, скачущих таймеров и пропажи кадров.
5. До какого-либо перевода рабочих пользователей проверены резервное копирование, восстановление, HTTPS, обновления и мониторинг.

**Не переключать рабочую игру**, пока все условия не выполнены. Для аварийного отката достаточно не изменять действующие URL/ключи frontend; этот эксперимент их вообще не трогает.
