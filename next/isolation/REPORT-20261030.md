# ГОС.ID и QWIZ-PARTY — отчёт о физической изоляции Supabase
Дата проверки: 30.10.2026. Тип: аудит и проект миграции. Статус: **НЕ ПЕРЕКЛЮЧЕНО**.

> **Важно.** Этот документ фиксирует реальные результаты проверок API GitHub и read-only запросов к Supabase. В отчёте нет дампов пользователей, паролей, хешей, токенов или секретных ключей. До выполнения отдельного cutover следует считать ГОС.ID и QWIZ-PARTY связанными общим backend.

## 1. Запрос и определение готовности

Цель: ГОС.ID и QWIZ-PARTY должны пользоваться **разными физическими Supabase-проектами**, не только разными префиксами таблиц. У каждого проекта собственные PostgreSQL, API endpoint и ключи, Auth, Realtime, storage и вычислительный бюджет. Приложения не должны обращаться к другому backend, запускать его триггеры, конкурировать за его пул соединений и добавлять запросы в чужую статистику.

Готовность нельзя объявлять на основании отдельных PostgreSQL-схем, префиксов таблиц, RLS, двух репозиториев GitHub, независимых браузерных вкладок или двух организаций Supabase с общим проектом.

- Supabase API показывает **один** доступный проект: `gos-sim`, ref `bderfrcfuhnutuoyudje`, регион `eu-central-1`, PostgreSQL **17.6**, статус ACTIVE_HEALTHY, организация на плане **Pro**. Указанный проект используется обоими приложениями.
- QWIZ `dimkazantsev/ORG`: старый `app.js`, `next/app.js`, `next/presenter.js`, `next/workspace.js` содержат `https://bderfrcfuhnutuoyudje.supabase.co` и публичный ключ. Это не изоляция.
- ГОС.ID `dimkazantsev/gos-sim1`: `lib/supabase.ts` читает `NEXT_PUBLIC_SUPABASE_URL` с fallback на тот же URL; `public-client-config.json` содержит тот же URL; production — Next.js/Vercel + Supabase.
- Обнаружены 57 таблиц семейства QWIZ/legacy в `public`: `qwiz_*` **36**, `org_next_*` **5**, `org_quiz_*` **16**; у всех включён RLS. Функций соответственно **95**, **10**, **32**. Отдельных представлений `org_quiz_*` **4**; пользовательских триггеров на `qwiz_*` + `org_next_*` **9**.
- 23 функции `qwiz_*` содержат ссылки на `org_quiz_*`. Это **текстовый подсчёт зависимостей**, не проверка полного транзитивного графа. Нельзя исключать legacy только по префиксу.
- Объём трёх семейств таблиц, включая их индексы и TOAST, по `pg_total_relation_size`: `qwiz_*` **2,842,624 байта**, `org_next_*` **557,056 байт**, `org_quiz_*` **2,334,720 байт**, всего **5,734,400 байт** (~5.47 MiB). Это **не** оценка полного dump, Auth, Storage или всей базы и не измерение дисковых операций.
- Предварительное пересечение QWIZ с `auth.users`: среди восьми выборочных QWIZ/legacy таблиц выявлено **11 уникальных связанных ID** из **57** пользователей auth. Это лишь **нижняя граница**: полный граф идентичностей и учётных записей ещё не выверен. Нельзя просто удалить остальных или механически копировать только эти 11 записей.
- `pg_publication_tables` для `supabase_realtime` содержит пять legacy таблиц `org_quiz_*`; `qwiz` использует также Broadcast через RPC. Настройки таблиц публикации, приватных каналов и RLS требуется перенести и протестировать отдельно.
- Обнаружены **9** текущих cron jobs; текстовый поиск по командам не выявил явных упоминаний `qwiz_` или `org_next_`, но не исключает косвенных вызовов. **НЕ КОПИРОВАТЬ cron задачи вслепую:** они могут относиться к ГОС.ID.
- У проекта две Edge Functions: `org-resolve-image` (вероятный владелец QWIZ — требуется проверка исходника) и `chat-media-cleanup` (вероятный владелец ГОС.ID — требуется проверка). Границы владения не установлены только по названию.

## 3. Предлагаемая итоговая архитектура

```text
GOS.ID (Next.js on Vercel)                  QWIZ-PARTY (GitHub Pages)
  NEXT_PUBLIC_SUPABASE_URL                    все frontend entrypoints
    |                                            |
    v                                            v
  gos-sim / bderfrcfuhnutuoyudje           НОВЫЙ ПРОЕКТ / новый ref
  [PG17, Auth, Storage, Realtime]           [PG, Auth, Storage, Realtime]
  [GOS tables, API, cron]                   [QWIZ + нужные legacy tables/RPC]
  НИКАКИХ QWIZ подключений                   НИКАКИХ GOS подключений
```

Выделение проекту QWIZ нового ref обязательно. Вариант «вторая схема в старом PostgreSQL» неприемлем: остаются общие CPU/RAM, лимит соединений, WALS, storage, общие Realtime/Auth limits.

При текущем Pro-плане новые проекты той же организации оплачиваются отдельно (минимальный Micro обычно порядка $10/месяц сверх уже используемых кредитов, цена перед созданием подлежит отдельному персональному подтверждению). Альтернатива — отдельная **Free Plan организация** Supabase с до двух активных бесплатных проектов, но 500 MB PostgreSQL, shared CPU / 500 MB RAM, Free Realtime квоты и авто-пауза после недели неактивности. Беспрерывная эксплуатация может требовать Pro. Пользователь должен выбрать организацию и тариф до создания проекта.

**Не создавать платный проект, не повышать тариф и не выполнять перенос по умолчанию.**

## 4. Что входит в QWIZ migration closure

1. **Таблицы**: `qwiz_*`, `org_next_*`, нужные `org_quiz_*` плюс любые обнаруженные зависимости и триггеры, индексы, sequences, enums/domains, права/GRANT, RLS и политики.
2. **Функции/RPC**: `qwiz_*` (95), `org_next_*` (10) и подмножество `org_quiz_*` (не более 32), разрешения EXECUTE, `SECURITY DEFINER` проверка. Считать зависимость по PostgreSQL catalog + по вызовам из динамического SQL; текстовый поиск без полного теста недостаточен.
3. **Auth**: применимость существующих `auth.users` ID, `auth.identities`, Auth credentials/password hash, пользовательские данные `qwiz_student_accounts`, `qwiz_student_links`, teacher/owner и административные роли. Пользователи ГОС.ID, не относящиеся к QWIZ, не должны переноситься. Возможность переноса hash Supabase подтверждена документацией, но перенос **выборочных пользователей** требует собственного проверенного процесса. Новая подпись JWT ⇒ старые сессии могут требовать повторного входа.
4. **Realtime**: публикации `org_quiz_*`, `org-next-CODE` Broadcast, разрешения каналов, обработка reconnect/stale, никаких подписок на GOS. Не менять фактический контракт событий до проверки.
5. **Storage**: перенос *только подтверждённых QWIZ* buckets/objects (с реальными байтами и policies), публичные asset URL и подписи private URLs. Копирование одних записей `storage.objects` **не переносит содержимое файлов**.
6. **Edge Functions**: проверить принадлежность `org-resolve-image`, перенести исходный код и секреты только если QWIZ использует; `chat-media-cleanup` не переносить без доказательства необходимости.
7. **Публичный клиент**: оба входа `/ORG/` и `/ORG/next/`, преподавательская студия, projector, профиль и service worker. Все JS/HTML должны указывать на единый **новый** backend QWIZ. Публичный publishable key — допустим в браузере; service_role/secret категорически нет.
8. **ГОС.ID**: не менять приложение и SQL до проверки независимой работы после отключения QWIZ от общего Supabase. `public-client-config.json` и настройки Vercel остаются на прежнем endpoint.
9. **Наблюдаемость**: отдельные логи, quotas, REST/Reatime usage, сценарии доступа 40 участников. Сравнить перед/после без предположения о гарантированном ускорении.

## 5. Реальный порядок выполнения — без прерывания занятия

**Этап А. Снимок/резервирование**. Подтвердить отдельную организацию и стоимость; создать проект QWIZ. До создания — экспортировать полный бэкап исходной базы в защищённое хранилище, зафиксировать версии PG/extension, Auth policy/config, Storage buckets, Realtime/Edge. Нельзя выполнять production SQL миграцию «наугад». Определить окно отсутствия активных игровых комнат для финального cutover.

**Этап B. Подготовка staging на новом проекте**. Создать схему как *изолированное подмножество*, сохранив FK/таблицы/функции и права. Не накатывать 100+ исторических `next/migrations/*.sql` по алфавиту: есть повторяющиеся определения, ручные и QA rollback файлы. Проверить RLS deny-by-default. Загрузить тестовые QWIZ данные, проверить Auth и RPC. Появление пустой комнаты и страницы лобби без ошибок — обязательно.

**Этап C. Точечный перенос аккаунтов и данных**. Полная инвентаризация зависимостей перед копированием. Сохранять UUID ссылок учителей, членов команд, контента и прав. Не утекать чужими учётными записями и не переносить данные ГОС.ID. Контроль количества/связности каждой таблицы, контроль Storage checksum и выборочных экспортов. При несовпадении хеша/COUNT — остановка без cutover.

**Этап D. Изолированное тестирование QWIZ**. Собрать **непубличную** тестовую копию сайта с новым `SUPABASE_URL` и новым **publishable** ключом; original main/Pages не трогать. Проверить QR→студент→комната→раунд→результаты, 40 анонимных входов, 40 WebSocket-подписок, 40 одновременных ответов, устойчивость после обрыва, таймеры, секретный код, географию, флаги, бонусы, отсутствие повторного начисления. Старый облачный тест 26.10.2026 дал 40/40 ответов, p95 2073 мс; сравнивать **одинаковые** сценарии.

**Этап E. Финальный перенос**. На согласованное короткое окно запретить создание новых комнат QWIZ (без остановки ГОС.ID), дождаться завершения действующих сессий и дозалить только QWIZ изменения после первого снапшота. Сверить counts/идентификаторы, сохранить подтверждение. Опубликовать изменение конфигурации на QWIZ Pages **одним обратимым коммитом**, учесть service worker cache и уже открытые вкладки. Не делать dual-write в две БД, пока она не реализована явно идемпотентно.

**Этап F. Проверка и откат**. Проверить QWIZ и ГОС.ID (новая комната/опрос/Storage/Reatime), мониторить сутки как ориентир наблюдения, не как гарантию. Если не проходит — вернуть старую версию frontend и сообщения о переподключении, не удаляя новый сервер; учесть, что ответы, записанные в новой базе после cutover, не окажутся в старой автоматически. Для аварийного возврата потребуется согласованный snapshot/дельта данных либо временное запрещение записей, иначе риск потери результатов. Старые таблицы не удалять до полного доказательства безопасности.

**Этап G. Очистка общего проекта**. Только после резервных копий, периода наблюдения и явного перечня зависимостей: отдельно найти QWIZ данные, рабочие Auth аккаунты, edge functions, buckets, cron; удалить **только подтверждённые** чужеродные объекты. Нельзя `DROP SCHEMA public CASCADE` и нельзя массово удалять `auth.users`. Любое удаление — отдельный review и отдельная PR/операция.

## 6. Проверки безопасности и приёмки

- [ ] `curl`/SDK QWIZ обращается к **новому** project ref; `gos-sim1` только к **старому**.
- [ ] Независимый статус PostgreSQL, API, Realtime и Auth у каждого проекта.
- [ ] 40/40 идентичностей и соединений, 40/40 ответов, дубликаты не начисляют очки.
- [ ] Защищённые RPC не раскрывают верные ответы до фазы результата.
- [ ] ГОС.ID проходит вход преподавателя и участников, чат/публикации/ВСН, файлы и все ключевые сценарии.
- [ ] Обе базы сохраняют правильные RLS/GRANT, отдельные secret keys и политики.
- [ ] Данные QWIZ после переноса совпадают с исходной согласованной точкой; логическое восстановление проверено.
- [ ] Полный перенос Storage проверен содержимым, не только metadata.
- [ ] Supabase Dashboard/usage демонстрирует разделение по двум проектам.
- [ ] CI, edge functions, cron, QR, service worker и все публичные frontend entrypoints не ссылаются на старый backend QWIZ.
- [ ] В рабочем `gos-sim` не осталось активности от клиентов QWIZ после окна устаревших вкладок.
- [ ] Отдельный подтверждённый rollback plan и запрет удаления исторических данных до завершения.

## 7. Ограничения текущего аудита

1. Новый проект **не создан**: Supabase-организация сейчас **Pro**; перед затратами требуется выбор организации и подтверждение стоимости.
2. Выполнена только **read-only** проверка PostgreSQL и репозиториев. Не создана копия live data и **не проверено** восстановление.
3. Не проверены все `SECURITY DEFINER` RPC на уровне исходного кода по отдельности. Признаки использования наследуемых legacy объектов есть, но полный динамический closure пока не доказан.
4. Единичные размеры/количества являются **снимком на 30.10.2026**, могут измениться при дальнейшем использовании.
5. Внешние данные ГОС.ID и других сервисов не должны быть удалены ради получения красивой статистики/скорости.
6. Создание отдельной схемы внутри существующего проекта не решает задачу и не будет предложено как итоговое разделение.
